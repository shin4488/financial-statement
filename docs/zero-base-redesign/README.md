# 財務3表 可視化アプリ ゼロベース再設計

既存のテーブル・実装に縛られず、1から設計し直す場合の実装方針。
「日本基準とIFRSの共通化・個別化」「銀行・保険など特定業種フォーマットが現れても
コードの根幹を触らず拡張できる保守性」を最優先の設計ゴールとする。

技術スタックは現行踏襲を前提とする（Rails + PostgreSQL + GraphQL / React + TypeScript + Apollo + recharts）。

## 設計の核となる考え方

6社の実XBRL調査（[01_xbrl_format_research.md](01_xbrl_format_research.md)）から導かれた事実:

1. **「会計基準」だけでは形式は決まらない。** 同じIFRSでもBSが「流動/非流動分類」の企業と
   「流動性配列（無区分）」の企業があり、同じ日本基準でも一般事業会社と銀行では別形式。
   つまり取得・表示の単位は「会計基準 × 表示形式（presentation format）」である。
2. **1つの有報の中で基準が混在する。** IFRS企業でも単体財務諸表は日本基準。
   よって会計基準・形式は「有報」ではなく「財務諸表（連結/単体）」の属性である。
3. **どの基準・形式でも共通する骨格がある。**
   - BS: 資産合計 / 負債合計 / 資本（純資産）合計は全形式で取得可能
   - PL: トップライン収益とボトムの利益（税引前・当期）はほぼ共通（例外: 保険IFRS）
   - CF: 営業・投資・財務の3区分 + 現金同等物期首期末は**全形式で完全共通**
4. **形式ごとに固有の科目がある。** 流動資産（分類形式のみ）、経常収益（銀行）、
   営業費用一括（楽天型IFRS）など。

この事実に合わせ、**「XBRLの科目」と「グラフの見た目」を直接結合させず、
中間に正規化した勘定科目コード（canonical item code）を置く**3層構造にする:

```
[取得層] 形式別Extractor が XBRLタグ → 共通科目コードに正規化
              ↓
[保存層] 縦持ちの financial_statement_items（科目コード × 金額）
              ↓
[表示層] 形式別ChartBuilder が 科目コード → 汎用チャート構造（積み上げセグメントの列）
              ↓
[フロント] 科目を一切知らない汎用チャートコンポーネントが描画するだけ
```

## この設計が保守性の要求に応える理由

**新しい形式（例: 日本基準の保険業）への対応で必要な作業:**

1. 対象企業のXBRLを1件取得してタグを実測する
2. `Ingestion::Extractors::JgaapInsurance` を1クラス追加（タグ→科目コードのマッピング定義が本体）
3. `Charts::Builders` に保険用のBS/PLレイアウトを1クラス追加
4. `FormatDetector` の判定表に1行追加
5. 必要なら科目コードレジストリに `pl.insurance_revenue` 等を追加

**変更しないもの: DBスキーマ（マイグレーション不要）、GraphQLスキーマ、フロントエンド全体。**
既存形式のコードにも一切触れない（Open-Closed）。横持ちテーブル案（形式ごとにカラム/テーブル追加）
と比べたとき、この「新形式=クラス追加のみ・スキーマ凍結」が縦持ちを採用する最大の理由である。

逆に縦持ちの弱点（型安全性・集計の複雑さ）は次で抑え込む:

- 科目コードはDBの自由文字列にせず、**Rubyの定数レジストリで管理**し保存時に検証する
  （コードレビュー・grepが効く。マスタテーブルは作らない: コードと利用ロジックは必ず同時に変わるため）
- 値は「円のbigint」1種類に統一。比率・導出値はDBに持たず表示層で計算する
- **「値が取れない科目は行を作らない」**（NULLも0も保存しない）。0との区別問題が構造的に消える

## 全体アーキテクチャ

```
┌─ Ingestion（日次バッチ / バックフィル）─────────────────────────┐
│ Edinet::Client            EDINET API v2 の薄いラッパ              │
│ Xbrl::Document            XBRLインスタンスのfact検索プリミティブ   │
│ Ingestion::DeiExtractor   企業情報・会計期間・基準・業種コード     │
│ Ingestion::FormatDetector (基準, 業種DEI, タグ実在) → 形式判定    │
│ Ingestion::Extractors::*  形式別: タグ→科目コードのマッピング     │
│ Ingestion::ReportIngester 上記のオーケストレーション + 永続化      │
└──────────────────────────────────────────────────────────┘
┌─ DB ────────────────────────────────────────────────────┐
│ companies / reports / financial_statements /                       │
│ financial_statement_items（縦持ち）                                │
└──────────────────────────────────────────────────────────┘
┌─ Serving（GraphQL）──────────────────────────────────────┐
│ Reports::SearchQuery      検索条件（証券コード・CF符号）→ SQL     │
│ Charts::Builders::*       形式別: 科目コード→StackChart/Waterfall │
│ GraphQL Types             StackChart / WaterfallChart（汎用構造） │
└──────────────────────────────────────────────────────────┘
┌─ Frontend ───────────────────────────────────────────────┐
│ StackedBarChart / WaterfallChart（汎用・科目非依存）              │
│ StatementCard / ListPage（APIの構造をそのまま描画）               │
└──────────────────────────────────────────────────────────┘
```

## 共通化と個別化の境界（明文化）

| 関心事 | 共通 | 形式別に個別化 |
|---|---|---|
| EDINETからの取得・zip展開 | ✔（全形式共通） | − |
| DEI（企業・期間・基準）読取り | ✔ | − |
| XBRLタグ→科目コード | −（プリミティブのみ共通） | ✔ Extractor 1クラス/形式 |
| DBスキーマ | ✔（全形式同一） | −（行の内容だけ違う） |
| 比率・導出値・積み上げ構成 | −（計算ヘルパのみ共通） | ✔ ChartBuilder 1クラス/形式 |
| 債務超過・赤字の表示反転 | ✔（Builder基底の汎用処理） | − |
| GraphQLスキーマ | ✔（StackChart/Waterfallの汎用構造） | − |
| フロントの描画 | ✔（汎用コンポーネントのみ） | − |
| CFチャート | ✔（全形式で完全共通） | − |

## 対応形式ロードマップ

| presentation_format | 対象 | フェーズ |
|---|---|---|
| `jgaap_general` | 日本基準・一般事業会社（現行アプリ対応分） | 1 |
| `ifrs_classified` | IFRS・流動/非流動分類BS（武田・三菱商事・NTT型） | 1 |
| `ifrs_liquidity` | IFRS・流動性配列BS（楽天・東京海上型） | 1 |
| `jgaap_bank` | 日本基準・銀行（三菱UFJ型） | 2（設計・タグ実測済み） |
| `jgaap_insurance` ほか | 日本基準・保険/証券等 | 将来（実測してから追加） |
| `unsupported` | US GAAP等（本表の詳細タグが存在しない） | 表示不可として扱う |
